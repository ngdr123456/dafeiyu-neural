## 三、★★★ 而 N3 的真因，**我和他的假设都错了**

**Gemini 假设：** `train.py` 的 `except` 吞掉一轮 ⇒ `89 != 90`。
**我假设：** 台账恢复循环的无谓 I/O ⇒ 文件忙异常 ⇒ 少一轮。

**❌ 两个都不是。**

**这一轮的基线又挂了一次，而这次 N3 的失败断言把它说清了：**

```
[FAIL] 【N3】训练进行中并发 decide：轮次照跑、控制状态不变、调用不阻塞
★ 有一次 decide 耗时 1.337 秒 —— 存在阻塞
```

**⇒ 是 `charter.decide_view()` 在一次并发里被拖到 **1.337 秒**，而 N3 的阈值是 **0.5 秒**。**
**⇒ **轮次一条都没少**（`added == 90` 那条断言过了），是**延迟**那条挂了。**

**⇒ 所以：**
```
· 不是逻辑缺陷
· 是 **decide 与训练线程同时写文件时的 Windows 瞬时延迟**
  （`decide_view` 要 `_append` 事件到 `C.ESCALATION`，而训练在写台账/character/carry）
· 我那一整天加的恢复循环守卫**确实减少了一点 I/O**，但它不是主因
· 单跑 10 次全过 —— 因为它是一个**尾部延迟**问题（p95 正常，偶发尖峰）
```

**★ 我没有去改 N3 的 0.5 秒阈值 —— 那是"改测试让它过"。**

**★★ 但我要如实说：这条测试在 Windows 上、在"整个测试套件同时跑两遍"的负载下，
0.5 秒的阈值本身就很紧。这是测试设计的鲁棒性问题，不是被测系统的缺陷。
判断权留给你们。**

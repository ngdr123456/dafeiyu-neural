# 证据续期问题（2026-10-28）

> **状态**：✅ **已解决**（同日）。下面保留原始记录，第一节写解决结果。
> **性质**：工程结构问题，不是判据问题。
> **原影响**：每改一行代码要重跑约 25 分钟；4 条证据永久 False，行动方案指向已做完的事。

---

## 〇、结论（先说结果）

**两半都解决了，而且第二半比我原以为的便宜得多：**

```
① 「改一行就要重跑 25 分钟」
   → source_hashes 从 170 个文件缩到 67（不再绑 tests/ 与 tools/）

② 「4 条证据无生成器、永久 False」
   → **我判断错了。它们有生成器，而且全是离线的。**
```

**四条续期的实际成本（全部离线，一次 API 没花）：**

```
tools/trial_relational_memory.py      passed=true   3 cases
tools/trial_self_action.py            passed=true   5 cases
tools/trial_organisation_runtime.py   passed=true
tools/trial_self_goal.py              passed=true   7 cases
```

**效果：**

```
改前  next_action = STRUCTURE_CAUSAL           过期证据 4 条
改后  next_action = **GOAL_RULE_INTEGRATION**  过期证据 **0 条**
      ✓ 基线 ✓ LIVE 门 ✓ 关系基础
      ✓ 组织规则执行 ✓ 自身动作修订 ✓ 声明目标流程
```

**★ 由此证实：`STRUCTURE_CAUSAL` 那个"下一步"是**假的** ——
  不是代码没写，是四条证据过期，让方案以为"那些事还没做"。**

**★ 而这也暴露一个设计特性：`choose()` 的嵌套 if 是"哪个前置信号缺失就去做那一步"的阶梯。**
**  证据一过期，缺失的就是"已完成"，于是让人重做已完成的事。**
**  ⇒ 这不是 bug，是把"证据新鲜度"当成了"完成度"。**
**  ⇒ 缓解办法就是这次的 source_hashes 缩窄（减少误过期），以及续期难度低（离线可跑）。**

## 一、现象

`engine/action_plan.py` 的 `source_hashes()` 绑定：

```python
for directory in ("engine", "tests", "tools"):     # ← ★ tests 和 tools 也在里面
    files.extend((root / directory).glob("*.py"))
files.extend((root / "state").glob("*.py"))
for directory in ("rules", "corpus"):
    files.extend(p for p in (root / directory).rglob("*") if p.is_file())
if (root / REGISTRY).exists():
    files.append(root / REGISTRY)
```

**共 170 个文件。**

7 个验证文件把自己的 `source_hashes` 写进报告；`action_plan` 要求
「报告的 `source_hashes` == 当前 `source_hashes`」才算"新"。

**⇒ 改任何一个文件，全部验证证据同时失效。**

## 二、实测代价（今天）

```
为了让证据有效，我重跑了：
   基线 verify_next_step.py   **4 次**（每次约 5 分钟）
   LIVE verify_self_goal_live **3 次**（每次约 25 分钟，8 次 API 调用）
```

**其中至少两次是白跑**，原因：

```
① 我在 tools/ 下建了临时补丁脚本 → 污染 hash 集合 → 刚跑的证据立刻失效
② 我在 tests/ 下建了 mutation 运行器 → 同上
③ 我在 tools/ 下留了 _trial_self_goal.bak.py → 同上，且一直留着
```

**⇒ 一个**为验证而写的工具**，会让**它要验证的那次结果**作废。**
**这是设计上的自相矛盾。**

## 三、更严重的一半：4 条证据**无法续期**

```
关系基础        passed=True  hashes=过期  ← 无生成器
组织规则执行     passed=True  hashes=过期  ← 无生成器
自身动作修订     passed=True  hashes=过期  ← 无生成器
声明目标流程     passed=True  hashes=过期  ← 无生成器
```

**⇒ 它们验过（10-08 的代码），但对当前版本**没有证据**，而且没有任何工具能重跑。**

**⇒ 所以 `relational_foundation_fresh_pass` 等 4 个信号**永久 False**。**

**★ 必须说清：这个 `False` **本身是对的**。**
**它验的是旧代码，现在的代码改过了，我们确实没有当前代码的证据。**
**问题不是"判太严"，是**没有续期手段**。**

## 四、三个候选修法

```
(甲) 给那 4 条补生成器
     ⇒ 根治，但要写 4 个测试工具
     ⇒ 而且不解决"每次改代码都要重跑"的问题

(乙) 承认它们是"10-08 代码的证词"，从判优先级里摘掉
     ⇒ 已部分执行：加了 stale_evidence 信号**列出**它们，
       但**没有**改 choose() 的 if 链（风险最小）
     ⇒ 结果：next_action 仍受它们影响

(丙) ★ 缩窄 source_hashes 的绑定范围
     现在绑 engine/ tests/ tools/ state/ rules/ corpus/ REGISTRY（170 个）
     系统的**运行时行为**只取决于 engine/ + rules/ + corpus/
     tests/ 和 tools/ 是**验证基础设施**，改它们不改系统行为
     ⇒ 改成只绑 engine/ + rules/ + corpus/
     ⇒ 立刻解决"临时工具污染"（今天犯了 3 次）
     ⇒ 但**不解决**那 4 条已过期的（它们的报告里存的是旧口径的 dict）
```

**⇒ 三者关系：**

```
(丙) 解决"以后改代码不再动辄 25 分钟"
(甲) 解决"那 4 条能不能续"
(乙) 解决"在那 4 条续不上时，判优先级别被假信号带偏"
⇒ **(丙) 最急，(甲) 最贵，(乙) 是权宜**
```

## 五、我的建议

```
先 (丙)：一行改动，立刻止血（不然每改一行都是 25 分钟）
再 (乙)：让 stale_evidence 真正参与判断，而不是只列出来
(甲) 以后按需补，不一次写完
```

**⚠️ (丙) 有个必须接受的后果：**

```
之后改 tests/ 或 tools/ 不再使证据失效
⇒ 但也意味着：**如果某个工具的行为改了（比如 trial_self_goal 改了判据），
   系统运行时不受影响，但"验证的严格程度"变了，而那不会体现在 hash 里**
⇒ 所以 (丙) 要配一条纪律：**改验证工具本身时，手动重跑相关证据**
```

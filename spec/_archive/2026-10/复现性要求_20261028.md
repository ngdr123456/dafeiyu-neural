## 一、事由：一次假警报

`spec/当前行动方案.json`（10-08 20:40）的 `next_action = REPAIR_CONTENT`，理由是
两个「未解决内容失败」：

```
① live:actual_conflict_quotes_complete
② live:component_not_passed:spec/有界目标承诺模型诊断_20261008.json
```

**排查发现 ①② 其实是同一个 case（那个文件 5 个 case 只有这一个没过）。**

## 二、复核：不是代码 bug

```
离线（注入假 reader）     7 / 7 全过
在线 2026-10-08（Codex）  4 / 5，targets = **1**
在线 2026-10-28（重跑）   5 / 5，targets = **2**      ← 代码一行未改

模型同为 deepseek-flash｜同为 temperature=0（understand.py:143）｜输入相同
两次 model_reason 完全不同：
  10-08「来源未见更改，可按原样逐字引用该证据」
  10-28「需保留两条相互冲突的原始说法，不能只引用其中一条」
```

**⇒ live 单次运行**不确定**。而验收把「一次 live 全过」当 gate：**

```
5 个 case 各 90% 稳定 ⇒ 全过概率 ≈ 0.9^5 ≈ **59%**
⇒ 四成概率因运气不好判「失败」
```

## 三、实证：不稳定不是某一个 case，是整套

加两遍比对后，**同一次运行**里就抓到了：

```
第 1 遍  actual_source_change_reconsider  True
第 2 遍  actual_source_change_reconsider  **False**   ← 翻了
（而上次挂的 actual_conflict_quotes_complete 这次两遍都过）
```

**⇒ 换一个 case 挂。说明不稳定是**整套 live 判据**的性质。**

## 四、改动

### ① `tools/trial_self_goal.py`

```
把 live 块抽成 live_chain(root)，**整条链跑两遍**
（5 个 case 串行依赖，不能单独重跑单个 case）

每个 case 记：run1_passed / run2_passed / agree / unstable
  passed  = run1 and run2                       ← 两遍都过才算过
  unstable = (run1 != run2)                     ← 单独可见
顶层新增 unstable_cases
```

### ② `engine/action_plan.py`

```python
# 抽样不稳 ≠ 系统缺陷（实证见上）
signals["live_unstable_cases"] = list(goal_live.get("unstable_cases") or [])
...
if case.get("passed") is False and **not case.get("unstable")**:
    → 才进 unresolved_content_failures

"live_fresh_pass": ... and not (goal_live.get("unstable_cases") or [])
```

**⇒ 效果：**
```
unstable 的 case  **不进失败清单**（不冒充缺陷）
                   **但单独可见**（不静默丢弃）
live_fresh_pass    要求「没有 unstable」
```

**⚠️ 一个自己犯的错，记下来：** 第一版从 `live`（真实诊断）读 `unstable_cases`，
但那东西只写在 `goal_live`（模型诊断）里 ⇒ 永远读到 `[]`。
**构造函数写对了，读错了源。** 已修。

## 九、这一轮的教训（写给自己）

```

  ① 说「三关全堵在语义验证」→ 其实两关硬编码 False

唯一做对的是**先怀疑「这次失败可不可复现」** —— 那个怀疑救了整轮。
```

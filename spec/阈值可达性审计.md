## ★ 机制盲区：死规则检测器为何没覆盖 `error_high`

### `admin.py` 的 `check_dead_rule` 是怎么判的

```python
allc = [c.id for c in M.conditions(M.MechanismConfig())]   # 机制**条件表**的全部条件单元
seen = Counter((r.get("mech") or {}).get("phase") for r in rows if r.get("mech"))
never = [c for c in allc if c not in seen]                  # 台账里从未出现过的
```

### 它为什么抓不到 `error_high`（四条，逐层递进）

| # | 原因 |
|---|---|
| 1 | **粒度不对**：它扫的是 `conditions()` 表里的**条件单元 id**，而 `error_high` 是 `MechanismConfig` 里的**阈值常数**，**根本不在那张表里** —— 连被扫的资格都没有 |
| 2 | **载体不对**：`error_high` 的四个使用点里，`mechanism.py` 的 `gate_open` 是一个**赋值**、`character.py` 的 R2 在**性格层**、`devlevel.py` 的失效判定在 **DevLevel** —— 三处都不属于机制条件表 |
| 3 | **判据类型不对**：它判的是「**某个分支有没有被走到**」（离散命中统计）；而阈值够不着是「**某个值有没有可能越过某条线**」（连续域分析）。**前者看 `phase` 的取值集合，后者要看变量的值域** —— 两种问题在台账里长得完全不一样 |
| 4 | **表象会骗人**：阈值够不着时，台账里 `phase` **照常变化**（其他条件在正常触发），所以 `never` 列表里干净得很、检测器报「0 条死规则」。**它只会说「这个分支没走到」，不会说「这个分支走不到」** |

### 一句话

> **`check_dead_rule` 检的是「命中集合」，不是「值域」。**
> `error_high` 这类缺陷在它眼里是一片安静 —— 因为**没有任何一条 `phase` 因为够不着阈值而消失**。

### 本次审计补上的正是这个盲区

本脚本不统计命中，而是对每条「变量 vs 阈值」比较**同时算两路**：

```
① 数学上界  —— 从公式推该变量的理论极值（上界从源码读，不重实现）
② 实测极值  —— 三个台账取 min/中位/max（demo 单列）
两路都不够阈值 → 不可达（确认缺陷）
```

## 审计本身的局限（如实标出）

1. **审计项是手录的**（10 条），不是自动扫全项目。自动化扫描「数值 vs 阈值」的比较在 Python 里做不可靠（属性的运行时来源难静态定）
2. `fail_tension`（第 10 条）**台账不记**，所以实测那栏用的是 `tension` 近似 —— 该条判「不可达」靠的是**前置条件恒假**，不是实测
3. 第 3 条（R2）的 `structure` 是由 `e / 0.60` 现算的，**不是台账原生的字段**，属推导量
